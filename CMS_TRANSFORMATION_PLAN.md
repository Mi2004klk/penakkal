# Penakkal — CMS Transformation Plan & Phased Implementation Roadmap

**Document status:** Implementation-ready plan · September 2026
**Scope:** Full audit of the existing Next.js platform + complete design for a dynamic, CMS-driven, media-optimised, production-ready system
**Relationship to `plan.md`:** `plan.md` (v4.0/v4.1) is the QA record of the *static frontend rewrite*. This document supersedes it as the roadmap for the *dynamic CMS transformation* and absorbs its unresolved findings.

- **§1–2** — Executive summary and the full current-state audit (what to preserve, what's broken, what's hardcoded).
- **§3–6** — Target architecture: stack decisions, database schema, media pipeline, CMS module map.

Verdict up front: **do not rewrite the application.** The public frontend (design system, article experience, accessibility layer, SEO scaffolding) is genuinely good and was hardened through four audit rounds. The correct strategy is to **keep the public site's component layer, replace its data source** (build-time JSON files → PostgreSQL + CMS), and **build the admin as a new route segment** (`/admin`) inside the same Next.js app. The phases below are ordered so the site never regresses: every phase ends with a deployable system.

## 1. Executive summary

Penakkal today is a **static, build-time-frozen publication**: 695 articles flow one-way from a WordPress export (`source-data/blog_export.json`, 14 MB) through five Node scripts into JSON files that Next.js reads at build time. Every content change — even fixing a typo — requires a developer to edit data and re-deploy. There is no database, no admin panel, no authentication, no API, no form backend, and no media management.

The audit found:

- **A strong frontend worth preserving**: a tokenised Tailwind v4 design system with CI-enforced WCAG contrast, an excellent focus-trap/overlay system, good skeletons/empty states, thoughtful Tamil/Arabic typography handling, and a hardened build-time HTML sanitizer.
- **Serious architectural debt**: 608 MiB git history carrying 601 MB of WordPress uploads, a duplicate copy of the entire old site (`existing_remote_backup/`), a non-deterministic build that calls the Gemini API and re-runs sharp over ~1,000 images on every deploy, and the same article HTML stored three times.
- **Real bugs shipping today**: every listing page inherits the homepage's canonical URL (a site-wide SEO defect), reading history silently stops recording after the first article per session, unknown tag/author URLs return HTTP 200 soft-404s, 212 article images still hotlink `http://penakkal.com` (mixed content), and 507 of 523 in-article images have empty `alt` text.
- **No operational safety net**: zero automated tests, no CI, a dead `lint` script (`next lint` was removed in Next.js 16), no backups, no error monitoring, no CSP.

The transformation plan converts this into a **database-backed, admin-managed platform** on nine phases:

| Phase | Name | Outcome |
|---|---|---|
| 0 | Stabilize & Clean | Repo hygiene, CI, critical bug fixes, deterministic builds |
| 1 | Data Foundation | PostgreSQL + Prisma + full schema + one-time import of all content & media inventory |
| 2 | Admin Core | Auth, RBAC, admin shell, users, audit log, settings v1 |
| 3 | Media Library | Complete media management: upload, variants, dedup, folders, focal points, safe replace/delete |
| 4 | Content CMS | Articles editor (Tiptap), workflow, revisions, categories, tags, authors, scheduling |
| 5 | Site Experience CMS | Pages & block builder, menus, homepage curation, settings v2, FAQs/testimonials/banners, real newsletter |
| 6 | Dynamic Public Platform | Public site switches to DB + ISR, server pagination, server search, SEO overhaul |
| 7 | UI/UX Production Polish | Systematic a11y, states, admin UX, motion & mobile refinement |
| 8 | Hardening & Launch Ops | CSP, rate limits, backups, monitoring, runbooks, go-live review |

### 2.2 What works well — preserve

1. **Design system discipline** — Tailwind v4 `@theme` semantic tokens (`text-heading`, `bg-surface-card`, z-index ladder), dark mode via token re-declaration only, print stylesheet, `content-visibility` on long prose (`globals.css:482`), documented in `DESIGN.md` with contrast gates (`scripts/verify-contrast.mjs` runs in `npm run build`).
2. **Meta/content data split** — 1.27 MB list metadata vs per-slug content files, double-cached through `react/cache` (`src/lib/articles.ts:12-52`). This seam is *exactly* where the DB repository layer will slot in.
3. **Build-time sanitization** — `sanitize-html` allowlist + Cheerio pre-pass + YouTube/Vimeo iframe host allowlist (`scripts/process-json.mjs:180-190`). The imported corpus is clean; the CMS must enforce the same policy at *save* time.
4. **Overlay/interaction system** — `Overlay.tsx` (focus trap, scroll lock with scrollbar compensation, history-aware close, reduced motion) is the strongest component in the repo and becomes the base for all admin modals/drawers.
5. **Accessibility baseline** — `lang="ta"`, `dir="rtl" lang="ar"` on Arabic blocks, skip link, combobox search palette, radiogroup font-size control, 44 px touch targets, `prefers-reduced-motion` kill-switch.
6. **Article reading experience** — reading progress, TOC with IO tracking, related articles with reasons, share bar, Jazakallah closing, print styles.
7. **SEO scaffolding** — per-article `generateMetadata` with OG article type, JSON-LD (Organization, WebSite+SearchAction, Article, BreadcrumbList, CollectionPage), sitemap with thin-content filtering for authors, RSS with CDATA.
8. **URL-driven list UX** — filters/sort/page in query params (`ArticleListClient.tsx:78-84`) — shareable and back-button friendly.

### 2.4 Architectural weaknesses

1. **Content is code.** All editorial content lives in generated JSON committed to git; edits require a developer and a full rebuild (data pipeline ~ minutes, `next build` of ~1,100 pages).
2. **Non-deterministic, destructive build.** `build = test:spacing && test:contrast && knip && data:all && next build` (`package.json:7`) mutates tracked intermediates in place, re-runs Gemini categorization (network + rate-limit sleeps inside the build), re-runs sharp over ~1,000 images, and has no atomic writes — an interrupted deploy corrupts data files.
3. **Data stored 3×.** Article HTML exists in `blog_export.json`, `articles.json` (intermediate), and `articles-content/*.json`; `coverBlur` is generated twice with different settings; `articles.json` + export are committed but never read by the app.
4. **Repo is a data vault.** 608 MiB pack: 601 MB `source-data/uploads/` (13,127 files incl. WP thumbnail variants and junk like `GeoLite2-Country.mmdb`), 697 generated data files, and an entire previous deployment `existing_remote_backup/` (781 tracked files, its own `package.json`/`next.config.ts`/21 MB data file — a nested Next app that Vercel docs explicitly warn about).
5. **Everything frozen at build.** Hadith-of-the-day (`HadithBanner.tsx:22-26`) and footer year are build-time constants; no `revalidate` on any route.
6. **1.27 MB client payload on listing pages** — `/blog` passes all 695 articles (incl. base64 LQIP strings) into a client component (`blog/page.tsx:30`).
7. **Synthetic taxonomy of low quality** — categories from a hardcoded Tamil keyword map + optional LLM; 40% land in `general`; tags are keyword artifacts; authors are regex guesses with junk values (article prose captured as an author name) and transliteration duplicates.
8. **Duplicated archive logic** — `category/[slug]`, `tag/[slug]`, `author/[name]` are ~100-line near-clones; the home page duplicates `PageShell` markup.
9. **Nav logic contradictions** — curated order includes `fiqh`/`spirituality` (3–4 articles) which can never appear because top-6-by-count gates them out; `general` (the largest bucket) does appear (`articles.ts:74-91`).
10. **Type system lies** — `Article` declares `content/wordCount/quranRefs/hadithRefs/lang` as required, but every entry in `articles-meta.json` lacks them; works only because `JSON.parse` is cast (`articles.ts:18`).

### 2.8 Security posture

**Strong:** build-time `sanitize-html` allowlist + iframe host allowlist; `noopener noreferrer` on external links; security headers in two layers (HSTS preload, nosniff, DENY framing, referrer/permissions policies); `poweredByHeader: false`; no server-side attack surface today (one static route handler only); no secrets in git (`GEMINI_API_KEY` env-only).

**Gaps:** no CSP (largest single gap given 695 innerHTML-rendered articles + 22 YouTube iframes); render-time regex rewriting *after* sanitization (`blog/[slug]/page.tsx:161-176`) is a fragile pattern; `X-XSS-Protection` obsolete header; RSS built by string concatenation with no XML-escape layer (`]]>` injection possible in principle); header duplication across two config files diverging (HSTS/cache only in `vercel.json`); tracked `.jetro/daemon/credentials.json` path; `existing_remote_backup` contains an *unsanitized* HTML pipeline — quarantined hazard if ever re-deployed.

### 2.9 Performance findings

- Listing pages ship the full 1.27 MB meta array to the client (RSC payload) — worst offender.
- 695 + 399 taxonomy/author pages prerendered per build with no ISR → builds are slow and content staleness is structural.
- Search fetches the whole 166 KB manifest and filters linearly per keystroke; `/search` renders unbounded results (limit `0`).
- Good foundations already present: meta/content split, `content-visibility` on prose, transform/opacity-only animations, manifest prefetch on idle, blur-up LQIP covers, `prose-article` print/perf rules.
- framer-motion bundled for effectively 3 components (Overlay, ReadingProgress, ViewToggle) — acceptable; keep.

`role="listbox"` contains a non-option `<button>` (`SearchModal.tsx:166-201`); About-page Arabic dua lacks `lang="ar" dir="rtl"` (`about/page.tsx:41-43`); heading levels skip h1→h3 on archive pages; stretched-link cards read the title twice for screen readers (`ArticleCard.tsx:21,38,96`); error/404 pages render no landmarks or skip link; `EmptyState` titles are `<p>` not headings; single light-theme logo in dark mode; theme-toggle label flashes pre-hydration; focusable-selector string duplicated ×3 in `useFocusTrap` (doesn't exclude `disabled`/`visibility:hidden`).

Canonical bug (C1, most severe); `/search` (noindex) listed in sitemap (`sitemap.ts:18`); all 59 tag routes in sitemap but single-article tags noindexed at page level (inconsistent); author JSON-LD hardcodes a non-trailing-slash URL (`author/[name]/page.tsx:74`); OG images lack dimensions; no per-page `og:locale` overrides; no `keywords`; RSS `enclosure` hardcodes `image/webp`; paginated `/blog?page=N` URLs crawlable but absent from sitemap; **no redirects mechanism exists at all** — slug history is unmanaged (critical for the WP→Next migration era and for future edits).

## 3. Target architecture

### 3.1 Principles

1. **One Next.js app, two worlds.** `/admin/*` (dynamic, authenticated, noindex) and the public site (cached, ISR, CDN-first) share the design system, Prisma client, and validation schemas — nothing else.
2. **Never regress the public site.** Every phase ends deployable. The file-based data layer is swapped for the DB repository behind the *existing function signatures* (`getAllArticles`, `getArticleBySlug`, …) so page components barely change.
3. **Editorial HTML is rendered from structured data, not strings.** New content is authored as Tiptap JSON → rendered by typed React components (no new `dangerouslySetInnerHTML`); legacy imported HTML keeps its sanitized-render path until re-edited, converging over time.
4. **The DB is the source of truth; the build pipeline dies.** No network calls, no sharp, no LLM inside `next build`.
5. **Cache everything public, purge surgically.** Tag-based revalidation (`revalidateTag`) on every CMS mutation; sitemap/RSS regenerated on demand.
6. **Safe references over cleverness.** Media deletion can never break content (usage registry + trash); slug changes auto-create redirects; every mutation is reversible via revisions + audit log.

### 3.2 Stack decisions & rationale

| Concern | Decision | Rationale / alternatives considered |
|---|---|---|
| Database | **PostgreSQL — Neon** (serverless, branching) | Branching gives staging environments cloned from prod data for CMS testing; generous free tier; Vercel-native. Alternatives: Vercel Postgres (same infra, no branching), Supabase (more than needed — we build our own admin). |
| ORM | **Prisma** (with migrations; `@prisma/adapter-neon` or pg pool) | Typed client, migration history, Prisma Studio for ops debugging. Alternative: Drizzle (leaner, but Prisma's migration + schema-as-doc workflow suits a CMS team). |
| Auth | **Auth.js v5** — credentials (Argon2id), DB sessions, invite-only users, optional TOTP | No public signup (small editorial team); middleware-protected `/admin`; roles in DB. |
| Editor | **Tiptap (ProseMirror)** with custom extensions | HTML in/HTML out with structured JSON as truth; custom nodes map 1:1 to existing patterns (Arabic RTL span, Quran/Hadith refs, InfoBox, PullQuote, lazy YouTube, media image node). Alternatives: Lexia/Lexical (weaker HTML round-trip for this corpus), MDX (wrong for non-dev editors, Tamil + Arabic mixed-direction content). |
| Media storage | **S3-compatible object storage — Cloudflare R2** (zero egress) behind a thin `StorageAdapter` interface | Zero egress fees matter for an image-heavy site; adapter allows switching to Vercel Blob/S3 without touching app code. |
| Image processing | **sharp in an admin Route Handler** (already a dependency) | Presigned direct-to-R2 upload, then a processing step (queue or inline) generates AVIF+WebP variants, 400px thumb, blur LQIP. |
| Public rendering | **ISR with `revalidate` + `revalidateTag` on CMS saves**; search/feed/sitemap as Route Handlers/`generateStaticParams` hybrid | Keeps CDN-first performance of the current static site while making content live. |
| Admin mutations | **React Server Actions** (zod-validated) | Typed end-to-end, no REST boilerplate, CSRF-safe by construction; Route Handlers only where a raw HTTP endpoint is required (presign, search, feed, OG image, cron). |
| Search | **Postgres `pg_trgm` + normalized substring API** (server-side, paginated) | Tamil has no Postgres stemming dictionary; trigram + NFC normalization gives fuzzy substring matching on any script at this corpus size. Client manifest retained as instant-first-screen fallback during transition. Upgrade path: Meilisearch/Typesense if corpus or traffic demands. |
| Validation | **zod** shared between server actions, admin forms, and import scripts | One schema per entity, reused everywhere. |
| Rate limiting | **Upstash Redis** sliding window | Auth, search, contact, newsletter, upload endpoints. |
| Scheduler | **Vercel Cron** → `/api/cron/publish` | Scheduled articles, trash purge, sitemap ping, nightly dump trigger. |
| Errors/monitoring | **Sentry** (client + server) + Vercel Speed Insights; **one** analytics product (recommend Plausible; drop Vercel Analytics + Speed Insights or keep Insights only) | Today: triple analytics. |
| Styling | Keep Tailwind v4 tokens; extend `DESIGN.md` tokens into admin | Zero migration cost; admin inherits contrast gates. |

### 3.4 Rendering & caching strategy

| Surface | Strategy | Invalidation |
|---|---|---|
| Article page `/blog/[slug]` | `generateStaticParams` for published; `revalidate: 3600` + `cacheTag('article:{slug}')` | `revalidateTag` on save/publish; new slugs get on-demand ISR |
| Listing/archives | Server-paginated RSC (24/page), `cacheTag('articles')` | same tag on any article mutation |
| Home page | `revalidate: 600` + tags `home`, `articles` | homepage config save or article change |
| Pages (`/about`…) | Per-page tag `page:{slug}` | page/blocks save |
| Menus/settings | Cached query helpers with tags `menu:*`, `settings` | respective saves |
| Sitemap `/sitemap.xml` | Route Handler, `Cache-Control: s-maxage=3600`, built from DB with the same noindex rules as today | purge on publish/unpublish |
| RSS `/feed.xml` | Route Handler from DB; real `lastBuildDate` | purge on publish |
| Search `/api/search` | Dynamic (rate-limited), ≤20 results/page, pg_trgm | n/a |
| Admin | `dynamic = 'force-dynamic'`, `noindex`, no CDN cache | n/a |
| Media variants | `Cache-Control: public, max-age=31536000, immutable` (hashed keys) | never (new hash on replace) |

### 3.5 API architecture

**Server Actions (admin, all zod-validated, RBAC-checked, audit-logged):**
`articles.*` (create/update/publish/schedule/unpublish/archive/restoreRevision/previewToken), `categories.*`, `tags.*` (incl. merge), `authors.*` (incl. merge), `media.*` (updateMeta/move/trash/restore/replaceFile/deleteForever), `pages.*`, `blocks.*`, `menus.*`, `settings.*`, `users.*`, `redirects.*`, `faqs|testimonials|banners|hadiths.*`, `newsletter.*` (admin), `contactMessages.*`.

**Route Handlers:**
- `POST /api/admin/upload-presign` — returns presigned PUT + creates pending `media` row.
- `POST /api/admin/media/[id]/process` — triggers sharp variant generation (or cron-drained queue).

## 5. Media & image management design

### 5.1 Upload pipeline

```
Admin UI ── select files ──▶ POST /api/admin/upload-presign  (auth+RBAC+rate limit)
          ◀── { mediaId, uploadUrl, headers } ── pending Media row created
     ── PUT original bytes straight to R2 (presigned, single-flight) ──▶
     ── POST /api/admin/media/{id}/process ──▶ sharp pipeline:
          1. sniff real type (file-type) — reject spoofed extensions
          2. validate: jpeg/png/webp/avif/gif/svg*(admin-only + sanitise), ≤10 MB (25 MB keep-original)
          3. strip EXIF/GPS (keep orientation), re-orient
          4. variants: widths [640, 828, 1080, 1200, 1920] × {avif q50, webp q72}
             + thumb 400×400 (cover-crop w/ focal) webp
             + blur: 10×10 base64 LQIP (same recipe as today's coverBlur)
          5. store variants/{checksum}/{w}.{avif|webp}, originals/{yyyy}/{mm}/{checksum}-{safe-name}.{ext}
          6. write width/height/variants/duration to Media row; status → ACTIVE
```

- **Duplicates**: checksum lookup first — exact dupe returns the existing Media (and increments nothing; dedup is by identity). Near-dupe detection (perceptual hash) is a Phase 3 stretch goal — store `phash` column from the start.
- **SVG**: allowed only for ADMIN/OWNER, sanitized (`DOMPurify` server-side) or converted to PNG on upload.
- **Filename sanitization**: transliterate → `[a-z0-9-]`, collapse, cap length; the *display* `originalName` is preserved separately.

### 5.2 Library UX

- Grid (default) / list views; infinite scroll with count; filters: type, folder, *unused*, upload date, uploaded-by; search across filename/alt/caption/credit.
- Folders = flat path tree (`MediaFolder.path` "2026/ramadan"); a **Smart collection** "Unused" (no `MediaUsage` rows) powers cleanup.
- Bulk select → move to folder, trash, delete-forever (RBAC-gated).
- Detail drawer: preview (thumb + original), editable metadata (alt **required** warning with a11y counter across library, caption, credit, title), **focal-point picker** (click image → `focalX/focalY` stored 0–1; used by `object-position` and thumb crop), **Replace file** (uploads new bytes under the *same* Media id — new checksum/variants, references untouched, old files retained 30 days for instant rollback), **usage list** ("Used by: 3 articles, 1 banner" with deep links), copy-URL menu (original + each variant + `next/image` snippet), download original.

### 5.3 Safe references (the deletion contract)

1. Every render/save path that binds a media asset to content writes a `MediaUsage` row (cover fields, editor image nodes, block data, avatars, banners, settings OG images). Usage harvest also runs as a nightly reconciliation job scanning `contentJson`/`contentHtml` for `mediaId` references.
2. **Trash** (soft delete): media leaves the library grid, URLs keep serving (30-day retention), restorable in one click.
3. **Delete forever** is blocked while any ACTIVE usage exists — the UI shows exactly where it's used, with links to detach. After purge: storage objects (original + variants) deleted, Media row → `PURGED`, prior URL returns 410 via a tombstone map (no silent 404s, no broken `<img>` in cached pages).
4. **Replace** never changes identity — references stay valid forever.

### 5.4 Public delivery

- Variant URLs are immutable (`variants/{checksum}/…`) → `Cache-Control: public, max-age=31536000, immutable`, CDN-ready (R2 public bucket or Cloudflare in front).
- `next/image` with `remotePatterns` for the bucket host; `sizes` authored at the component level (fixes today's blanket `100vw`).
- Article body images render through the editor's image node component (widths/heights known → zero CLS, native lazy loading default, `priority` only for the cover).
- Legacy `/media/**` paths keep working: Phase 3 migrates files to R2 and adds a catch-all Route Handler redirecting `/media/*` → bucket URL (301, immutable), so old cached HTML never breaks.
- **AVIF+WebP** everywhere; cover images keep LQIP blur-up (identical UX to today).
- CDN readiness: all media URLs flow from one `mediaUrl(media, variant)` helper — pointing it at a custom domain or image CDN later is a one-line change.

### 5.5 One-time legacy migration (Phase 3)

1. Hash every file in `public/media/**` + register as `Media` rows (cover→field `cover`, content→`body` usages) with checksums (kills the hidden dupes), extracted dimensions, blank alt (flagged for editorial backlog — surfaces the 507-empty-alt debt as a visible worklist in the library).
2. Re-run variant generation for AVIF at all widths (covers are 1024px webp only today).
3. Fix the 36 Tamil filenames + 3 zero-width-space paths by re-keying to checksums (slugs untouched — pure storage concern).
4. Recover the 212 `http://penakkal.com` hotlinks from `source-data/uploads/` (verified present on disk) into the library; third-party hotlinks (16) get downloaded where licensing is reasonable, else flagged.
5. Backfill `MediaUsage` from `articles.coverMediaId` + a content scan.

### Phase 6 — Dynamic Public Platform: DB Swap, ISR, Server Pagination, Search, SEO Overhaul

**Objective.** Flip the public site from build-time files to the database with ISR — content edits go live in under a minute with no deploy — while fixing every remaining SEO/performance structural issue (§2.4, §2.9, §2.11) and retiring the legacy pipeline for good.

**Existing issues discovered.** 1.27 MB client payload on `/blog`; all pages frozen at build (hadith rotation, footer year); no ISR/revalidation; search is client-only substring with no body search, no Tamil normalization, undefined keys (fixed in Phase 0) and manifest maintenance burden; sitemap lists noindex `/search` and all tags indiscriminately; author JSON-LD URL bug; paginated URLs uncrawlable; RSS frozen; archive pages triplicated (~300 lines); home page duplicates `PageShell`; type-lie on `Article`.

**Required changes.**
1. **Repository swap**: public pages move from `lib/articles.ts` file readers to `lib/content/queries.ts` (Prisma) behind the same function signatures; delete `CONTENT_SOURCE` flag and the file readers; `generateStaticParams` for articles/categories/tags/authors stays (build-time seed set) + `revalidate` windows + `revalidateTag` from CMS saves. `export const revalidate = 3600` (articles), `600` (home), etc. per §3.4.
2. **Server-side pagination** on `/blog` and archives: 24/page RSC-rendered with the existing `Pagination` component converted to Links (SEO-crawlable); keep URL-driven filters (query params) resolved server-side; the client `ArticleListClient` slims to view-mode toggle + client-side sort of the current page or moves fully server-side — decision rule: ship ≤ 30 article cards to the client ever.
3. **Archive consolidation**: shared `<ArchivePage>` component for category/tag/author (hero + breadcrumb + paginated grid + JSON-LD); delete ~300 duplicated lines; home page adopts `PageShell`.
4. **Search**: `/api/search` (pg_trgm + NFC normalization + `simple` tsvector fallback for body text), paginated 20/page, highlighted server-side or client-highlight retained; `useSearch` rewritten against the API with the same debounce/keyboard UX; manifest generation removed once parity metrics pass (same-or-better relevance on a 50-query Tamil test set). Recent-search behavior fixed (save on explicit action only — kills the pause-typing pollution bug).
5. **SEO overhaul**: per-route canonicals everywhere (root-layout canonical removed in Phase 0 — now verified sitewide); sitemap from DB honoring noindex rules (drop `/search`, filter 1-article tags, add paginated blog URLs with `rel prev/next`-safe canonicals); author JSON-LD uses `absoluteUrl` + real Person entities; OG images via `/og/[slug]` (`@vercel/og`: title + cover + brand frame) with dimensions everywhere; RSS from DB with honest `lastBuildDate`, `content:encoded` summary, correct enclosure types, trailing-slash self-link; `robots.ts` from settings.
6. **Legacy retirement**: delete `data:*` from package scripts; archive `scripts/process-json.mjs` et al. to `scripts/import/legacy/` (they already ran as the Phase 1 importer); remove `src/data/**` and `public/search-manifest.json` from the repo; README rewritten to describe the dynamic architecture.
7. **Progressive enhancement pass**: streaming with Suspense boundaries per section (already partially present), `loading.tsx` retained, stale-while-revalidate semantics verified.

**Architecture/design decisions.**
- ISR + tags (not SSR-per-request): preserves the static site's CDN economics — the DB is hit on cache miss only; a saved article purges exactly its tag set.
- Server pagination is the single biggest performance win (1.27 MB → ~40 KB per listing view) and fixes crawlability simultaneously.
- The search API keeps the corpus server-side and unblocks body-text search (impossible with the manifest); trigram handles Tamil vowel-sign variants that raw substring misses.
- `/og/[slug]` dynamic OG images end the static `og-default.png` era for articles — measurable CTR improvement potential on social/WhatsApp (primary traffic channel per ShareBar emphasis).

**Database changes.** None structural. Query/index tuning: verify `pg_trgm` GIN usage, listing composite index, cover-author-category join plan (`EXPLAIN` review); add `Article.searchDoc` generated column if tsvector is adopted.

**Backend/API changes.** `/api/search`, `/og/[slug]`, sitemap/RSS/robots become DB-backed; CMS save hooks call `revalidateTag` (already present, now load-bearing); `getAllArticles` et al. deleted.

**Frontend/UI/UX changes.** Listing pages feel identical but paginate server-side (URL changes: `/blog?page=2` now server-rendered content, not client-filtered); search UI unchanged in behavior, new engine behind it; everything else invisible.

**CMS requirements.** All modules live; the public site is now the *rendering* of CMS state — this phase is where "manageable end-to-end" becomes literally true.

**Image/media requirements.** All public imagery already flows from the media library (Phase 3); this phase verifies `next/image` + `sizes` correctness per breakpoint and that `coverBlur` LQIPs are generated from library variants.

**Security & performance considerations.** Search endpoint rate-limited (per-IP sliding window) and paginated (no unbounded result render — closes the limit-0 issue permanently); ISR means origin load stays low; DB connection pooling via Neon pooler; all queries parameterized (Prisma); no client secrets; Lighthouse budgets enforced in CI (perf ≥ 90, CLS < 0.05 on article/listing/home).

**Dependencies.** `@vercel/og` (built in), pg_trgm (SQL), none else new.

**File/module-level implementation areas.** `src/lib/content/queries.ts` (becomes the only data layer), `src/app/{blog,category/[slug],tag/[slug],author/[name]}/page.tsx` (+ shared `ArchivePage` in `src/components/article/`), `src/app/page.tsx` (+ `PageShell` adoption), `src/hooks/useSearch.ts` (API rewrite), `src/app/api/search/route.ts`, `src/app/og/[slug]/route.tsx`, `src/app/{sitemap.ts,robots.ts,feed.xml/route.ts}`, deletions: `src/lib/articles.ts`, `src/data/**`, `public/search-manifest.json`, `scripts/{process-json,categorize,download-media,generate-metadata,validate-data}.mjs` (→ archived), `package.json` scripts, `README.md`.

**Testing & validation.**
- Parity crawl: for all 695 articles + all taxonomy pages, rendered HTML before/after swap diffed (ignoring whitespace/ordering) — zero content regressions.
- Search relevance set (50 Tamil queries incl. vowel-sign variants) — new API ≥ manifest baseline; latency p95 < 150 ms warm.
- Cache/purge e2e: edit article title in admin → public page reflects within 60 s; sitemap/RSS update; tag pages sharing the tag purge.
- Pagination e2e + crawl: rel prev/next semantics; `?page=999` → graceful empty state (200) vs `?page=abc` → 400/redirect.
- Lighthouse CI thresholds on 5 key routes.
- Load test (k6): 200 rps mixed read on home/article/search against staging with prod-size data — p95 latency and DB pool headroom recorded.

**Definition of Done.** `git push` no longer has any effect on content; every content/save action is live on the public site within one cache window; listing payloads < 50 KB; search covers body text with Tamil-aware matching; every §2.11 SEO finding closed and verified; the data pipeline exists only as archived importer history.

### Phase 7 — UI/UX Production Polish (Public + Admin)

**Objective.** Raise the whole product — reader-facing and admin-facing — from "works correctly" to "feels crafted": systematic accessibility, consistent states and feedback, refined typography/motion/mobile behavior, and admin ergonomics that make the CMS pleasant for daily editorial work.

**Existing issues discovered.** All §2.10 a11y findings (listbox-role violation, Arabic lang gap on About, h1→h3 skips, stretched-link double-reading, landmark-less error/404 pages, `<p>` empty-state titles, single-logo dark mode, theme-label flash); exactly one toast in the app; zero confirmation dialogs; three different "appear" animation strategies; admin forms still basic; grid-class duplication and six `mounted`-gates (Phase 0/6 cleanups leave some); store's unbounded bookmarks; Overlay double-open history edge cases; `RelatedArticles` reason labels can disagree with the server scorer; dark-mode logo contrast.

**Required changes.**
1. **Accessibility sweep (public + admin)**: fix every §2.10 item; `axe-core` in Playwright on 10 key routes (0 serious/critical); heading-order audit; stretched-link cards get a single accessible name (title link inside, card link `aria-hidden` duplicate removed); admin tables/dialogs get full keyboard + SR coverage; focus-visible styling standardised on the token system.
2. **Feedback system**: adopt Sonner (installed Phase 2) across all public interactions (bookmark saved, link copied — replacing the one-off inline statuses where appropriate while keeping `aria-live` semantics); shared `ConfirmDialog` (Modal-based) for every destructive action (clear history, remove bookmark bulk, admin deletes); undo patterns where cheap.
3. **State standardisation**: every async surface has defined loading (skeleton matching final layout), empty (with action), error (with retry), and success states — audited via a state-matrix checklist per route; optimistic updates for bookmark/theme with rollback.
4. **Public refinement pass**: article typography rhythm (measure, Tamil/Arabic line-height tuning), TOC/related/share spacing cohesion, card hover/focus consistency across 4 view modes, hero art direction on mobile, mobile nav micro-interactions, 404/error pages regain header/footer landmarks with helpful links, logo dark variant + brand mark polish.
5. **Admin ergonomics**: DataTable v2 (column prefs, density toggle, sticky header, saved filters), form patterns (dirty-state warning on navigation, autosave indicators, keyboard submit), editor polish (distraction-free mode, word-goal, Tamil spell-check hookup if available), image picker recent/featured tabs, dashboard widgets (missing-alt worklist, scheduled queue, stale drafts).
6. **Motion & consistency**: one reveal strategy (CSS `animate-fade-in-up` or IO-based, not three), spring tokens from `lib/motion.ts` used everywhere, all reduced-motion paths re-verified; admin adopts the same tokens (dark mode QA with the contrast gate extended to admin pages).
7. **Debt cleanup completion**: shared `VIEW_GRID_CLASS`, `useMounted()`, bookmark rehydration normalizer (single place), Overlay double-open history fix, related-articles reason from server payload, bounded bookmarks (500 + prune policy), dedup focusable-selector constant.

**Architecture/design decisions.**
- Polish is a *phase*, not a background activity, because it needs holistic passes (a11y audit, state matrix) rather than ticket-by-ticket dribble; but individual a11y *violations* found earlier are fixed in their phases when touched.
- Sonner + ConfirmDialog become the app-wide primitives — no more bespoke feedback code (the SavedContent undo toast is rebuilt on Sonner with identical a11y semantics).
- The state matrix (route × loading/empty/error/success) becomes a living QA document and a Playwright fixture-driven test suite.

**Database changes.** None (bookmarks/history remain client localStorage; if server-synced accounts are ever wanted, that's a future RFC — out of scope here by design).

**Backend/API changes.** Related-articles payload includes the ranking reason string (ends client re-derivation).

**Frontend/UI/UX changes.** This phase *is* frontend: ~40 component touch-points enumerated in the a11y/state matrices plus the admin upgrades above.

**CMS requirements.** Admin UX quality is itself a CMS requirement (editorial adoption depends on it); dashboard widgets expose the media worklists (missing alt) that keep quality debt visible.

**Image/media requirements.** Logo/brand dark-mode variants uploaded via media library and bound in settings; any new decorative art flows through the library.

**Security & performance considerations.** a11y and polish changes are mostly class/ARIA-level — bundle-size guard (knip + size budget in CI) prevents regressions; animations audited for main-thread work (transform/opacity only).

**Dependencies.** `axe-core`/`@axe-core/playwright`; otherwise none.

**File/module-level implementation areas.** `src/components/**` (per a11y matrix), `src/components/ui/{ConfirmDialog,Toast}.tsx` (new), `src/components/admin/**` (DataTable v2, forms, dashboard), `src/app/{error,not-found}.tsx`, `src/hooks/useMounted.ts`, `src/store/useStore.ts` (normalizer + bookmark bound).

### Phase 8 — Hardening, Observability, Backups & Launch Ops

**Objective.** Make the dynamic system *operationally* production-grade: locked-down security posture, real backups with restore drills, monitoring/alerting, performance headroom proven, and documented runbooks — then execute the cutover review and go live with confidence.

**Existing issues discovered.** No CSP despite innerHTML-rendered legacy content + 22 YouTube/Vimeo iframes; `X-XSS-Protection` obsolete header; header duplication/divergence between `next.config.ts` and `vercel.json`; no rate limiting anywhere (until Phases 2–6 added scoped limits); no backups of *anything* (previously moot for a static site — now the DB is the crown jewels); no error monitoring (`error.tsx` only logs to console); triple analytics; no redirect coverage for the original WP→Next URL history; no runbooks; Vercel cron security unverified.

**Required changes.**
1. **Security hardening**: single source of headers in `next.config.ts` (delete the duplicate block from `vercel.json`); add a **CSP** — `default-src 'self'`; `frame-src https://www.youtube-nocookie.com https://www.youtube.com https://player.vimeo.com`; `img-src 'self' <media-bucket-origin> data:`; `script-src 'self' 'unsafe-inline'` (theme bootstrap + Plausible if self-hosted else its origin); `style-src 'self' 'unsafe-inline'` (Tailwind + inline styles); report-only rollout → enforce; drop `X-XSS-Protection` and `interest-cohort`; secrets audit + rotation (DB, R2, Upstash, CRON_SECRET, AUTH_SECRET); dependency audit (`npm audit` + Dependabot); admin 2FA rollout to all ADMIN/OWNER accounts.
2. **Rate limiting complete matrix**: auth (per-IP + per-account), search, contact, newsletter, upload-presign, preview tokens — all through the Upstash helper with per-endpoint budgets + 429 semantics documented.
3. **Backups**: Neon automated snapshots (PITR window confirmed for the plan tier) + nightly `pg_dump` via Vercel Cron → R2 `/backups` (30-day retention, weekly full + daily incremental media manifest); R2 bucket versioning ON (media replace/delete recoverable at storage layer too); **documented monthly restore drill** (restore to scratch Neon branch, run parity script, record RTO).
4. **Monitoring & alerting**: Sentry (client + server, release-tagged, sourcemaps) wired into `error.tsx` and server-action error paths; uptime checks (Better Stack/UptimeRobot) on `/`, `/blog`, `/api/search`, `/feed.xml`; Vercel Speed Insights reviewed weekly; log-based alert on 5xx rate; cron-failure alerts (publish/trash-purge/dump); analytics decision executed (keep Plausible; remove Vercel Analytics + Speed Insights *or* keep Insights for CWV — one owner decision, documented).
5. **Performance proof**: k6 load profile (browse mix: 70% article, 20% listing, 10% search) at 2× current peak for 10 min on staging with prod-size DB — p95 targets: article < 800 ms (cache-cold), listing < 600 ms warm, search < 250 ms; DB pool and serverless function saturation recorded; Lighthouse CI budgets on 5 routes (perf ≥ 90, a11y ≥ 95, BP/SEO ≥ 95).
6. **Launch/SEO ops**: full redirect audit (WP-era URLs → current slugs where mappings exist; bulk import via Redirects CSV); Search Console + Plausible dashboards configured; sitemap ping after publish; `feed.xml` subscriber parity check; rollback runbook (Vercel instant rollback + DB point-in-time restore procedure); incident runbooks (DB down, R2 down, publish loop, malicious upload); **production readiness review** against a published checklist (this section).
7. **Post-launch observability window**: two weeks of daily checks (error rate, cache hit ratio, 404/410 top lists, cron success, backup integrity) before declaring the transformation complete.

**Architecture/design decisions.**
- CSP in report-only first (2 weeks of logs) — avoids breaking embedded legacy content blind; enforcement follows evidence.
- Backups are *restores waiting to happen*: the drill is part of the definition of done, not documentation.
- Analytics consolidation (3 → 1) is both performance (script weight) and decision-hygiene.
- The redirect module + audit closes the last SEO risk from a decade of WordPress URL history.

**Database changes.** None. (Optional: `Session` purge cron, `AuditLog` partitioning by month if volume demands — deferred by default.)

**Backend/API changes.** CSP + consolidated headers; Sentry init + instrumentation; cron additions (`db-dump`, `trash-purge` extension, `session-purge`); backup manifest generation.

**Frontend/UI/UX changes.** Minimal (Sentry client init; analytics script consolidation).

**CMS requirements.** Admin 2FA enrolment flow (flagged in Phase 2) completed for privileged roles; audit log retention policy set.

**Image/media requirements.** R2 versioning verified by restoring a replaced file in the drill; trash-purge cron proven (media retention policy end-to-end).

**Security & performance considerations.** This phase *is* the security/performance phase; the load test, CSP evidence, backup drill, and readiness checklist are the acceptance artifacts.

**Dependencies.** `@sentry/nextjs`; monitoring accounts (Sentry, uptime); Dependabot config; k6.

**File/module-level implementation areas.** `next.config.ts` (headers/CSP), `vercel.json` (reduce to redirects-only if needed), `src/instrumentation.ts`, `src/app/api/cron/{db-dump,trash-purge,session-purge}/route.ts`, `src/lib/rateLimit.ts` (matrix), `.github/dependabot.yml`, `docs/runbooks/*.md`, `docs/backup-restore.md`, `docs/production-readiness-checklist.md`.

**Testing & validation.**
- CSP report-only → zero reports for 2 weeks → enforce → re-crawl 50 random articles (iframes, media, inline styles all pass).
- Restore drill executed and timed (target: scratch DB live < 30 min, parity script green).
- k6 results documented against targets; failure-mode tests (DB pool exhaustion behavior, R2 5xx fallback for media URLs, Upstash outage → fail-open vs fail-closed per endpoint decision documented).
- Pen-test-lite: auth bypass attempts on admin actions (direct POST replay), rate-limit verification, upload of malicious files (EICAR, polyglot images, SVG-with-script) all rejected.
- Readiness checklist signed off by the site owner.

**Definition of Done.** CSP enforced with zero breakage; every external input point rate-limited; backups exist, restore proven; Sentry + uptime live with alerting; load test passed at 2× peak; analytics consolidated; runbooks published; two-week post-launch window green — **the system is production-ready and fully admin-managed**.

## 8. Cross-cutting concerns

### 8.1 Testing strategy (applies throughout)

| Layer | Tool | What |
|---|---|---|
| Unit | Vitest | zod schemas, RBAC matrix, slug/redirect logic, media variant pipeline (fixture matrix), reading time, search normalization |
| Integration | Vitest + test DB (Neon branch or pgTAP) | repository queries, importers, revision/restore, usage registry |
| Component | Vitest + Testing Library | block registry rendering, editor round-trip, DataTable states |
| E2E | Playwright | public journeys (home→article→bookmark→saved; search modal + page; pagination; theme/font-size persistence) and admin journeys (login→write→preview→schedule→publish; upload→describe→use→safe-delete; menu/page editing) |
| A11y | @axe-core/playwright | 0 serious on key routes (Phase 7 gate) |
| Visual | Playwright snapshots | 12 templates × light/dark × 3 viewports (Phase 7 gate) |
| Performance | Lighthouse CI + k6 | budgets in CI; load proof at Phase 6 & 8 |
| Data | Parity scripts | import equality (Phase 1), pre/post DB-swap HTML diff (Phase 6) |

### 8.2 Environments & deployment

- **Production**: Vercel (main branch) + Neon prod + R2 + Upstash.
- **Staging**: Vercel preview on `develop` (or per-PR previews) + Neon staging branch (branchable = CMS testing with realistic data). Preview deployments get `noindex` + basic auth via middleware.
- Migrations: `prisma migrate deploy` runs as a Vercel pre-deploy step or CI job gating deploys; forward-only policy; destructive migrations require a checklist entry.
- Feature flags: `CONTENT_SOURCE` (removed Phase 6), preview-token auth, CSP report-only→enforce, 2FA — all env-driven.

### 8.3 Analytics & SEO operations

- One analytics product post-Phase 8 (Plausible recommended — privacy-respecting, lightweight, already integrated).
- Search Console monitored weekly (coverage + canonical errors should drop to zero after Phase 6); sitemap pinged on publish; redirect hits reviewed monthly for pruning.

### 8.4 Cost & scalability outlook

- Neon free/starter tier comfortably serves this traffic with ISR; the DB is hit on cache miss only. R2 zero-egress keeps media costs flat with growth. Upstash free tier covers rate limits at this scale.
- Scaling levers, in order, if traffic 10×: longer ISR windows → Neon read replica → Meilisearch for search → Cloudflare in front of everything (media already CDN-ready by URL design).
- Content headroom: schema supports 100k+ articles without change (pagination, indexes, trigram search all sized for it); block registry and collections grow by code addition, not migration.
